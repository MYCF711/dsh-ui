## 空闲内存为什么超标：拆开看

**Viva 空窗口本身就要 67.2 MB。** 我们的 1000 条内容只加了 8.3 MB。

用 `GOGC` 调 Go 堆，几乎无效：

| GOGC | WorkingSet | Private |
|---:|---:|---:|
| 100（默认） | 75.4 MB | 88.3 MB |
| 50 | 74.4 MB | 84.6 MB |
| 20 | 74.1 MB | 84.9 MB |
| 10 | 70.6 MB | 86.6 MB |

**结论：这 67 MB 不是 Go 堆，是图形栈固定成本**（D3D11 设备 + 交换链 + DirectWrite/字体缓存 + 系统 DLL 映射）。**GC 调参救不了它。**

## 补充（06:24）：视口虚拟化的真实收益，用真界面量出来的

前面 E3 用的是"1000 条一次全渲染"的测试程序。这一轮把 U1 骨架接上 mockd，用 `-tail 1000` 与 `-limit N` 两档实测同一个会话：

| 配置 | WorkingSet | Private |
|---|---:|---:|
| 1000 条**全渲染** | **71.8 MB** | 113.0 MB |
| 1000 条只渲染 **60** | **60.8 MB** | 93.6 MB |
| 1000 条只渲染 **300** | 62.2 MB | 93.8 MB |

**虚拟化收益 = 11.0 MB WS / 19.4 MB Private。**

这验证了 §「还能再降的地方」里那条估算（**"估计再降 10–15 MB"→ 实测 11.0 MB**），误差在区间内。

**注意**：60 条那档（60.8 MB）已经接近空窗口基线（67.2 MB，且那次样本不同），说明**再往下压的收益会迅速衰减** —— 地板还是图形栈那 60 多 MB。

**所以 U1 的虚拟化目标定在"只渲染视口 ±1 屏（约 40–60 条）"，不做更复杂的滚动回收**：再做深也只能再省 2–3 MB，不划算。
