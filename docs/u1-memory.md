# U1 内存账：一条消息 0.46 MB

> 2026-11-03 09:40 · 真实会话（`docs/go/HANDOFF.md` 那个，442 条日志消息）· 单进程 · 无虚拟化

## 实测：内存与消息条数成正比

| `-tail`（渲染多少条） | WorkingSet | CPU |
|---:|---:|---:|
| **30** | **94.6 MB** | 1.14 s |
| 60 | 111.7 MB | 1.84 s |
| 100 | 128.4 MB | 2.59 s |
| **200** | **172.9 MB** | 4.16 s |

线性回归：

```
内存 ≈ 80.8 MB（基线）+ 0.46 MB × 消息条数
CPU  ≈ 4 ms（基线）   + 18 ms  × 消息条数
```

**基线 80.8 MB** 与空窗口实测量级一致（hello 67.2 MB，这里多了侧栏、输入框、Markdown 引擎）。

## 这不是 Markdown 的锅

我做过三组对照，把嫌疑逐个排除：

| 嫌疑 | 实验 | 结果 |
|---|---|---|
| Markdown 每帧重排 | 加 `text+width → height` 缓存 | **111.2 → 50.1 MB**（那条会话短，占比大） |
| 切会话不清理文档树 | `openSession` 里清空 `mdDocs/mdViews` | **无变化**（172.3 vs 172.9，噪声内） |
| 老消息用 Markdown 太贵（LOD） | 只保留最近 30 条走 Markdown | **无变化** |

**三个都排除了，剩下的就是渲染本身**：Viva 的 "GPU-composited text textures"（README 原话）——**每一条消息的每一行文字都是一块纹理**。200 条长消息的纹理加起来就是这个数。

## 所以 U1 的真正目标只有一个：虚拟化

| 方案 | 预计内存 | 说明 |
|---|---:|---|
| 现在（全渲染 200 条） | 172.9 MB | 已实测 |
| 只渲染视口 ±1 屏（约 10 条） | **≈85 MB** | 按 0.46/条 推算 |
| 加温缓存 5 个会话 ×10 条 | ≈85 MB | 缓存的是**数据**不是纹理，切回来重新出纹理 |

**关键区别**：之前估的"温缓存 3 MB/会话"是数据；这里是**纹理**，只有真正画出来的才有。所以虚拟化必须做在**渲染层**（只 `f.Slot` 视口内的消息），不是在数据层。

## 对 U1 的硬约束

1. **视口外的消息不进 flex 树**，不只是"不显示"——`f.Slot` 都不该建。
2. 每条消息的高度必须先算（`MarkdownView.Layout` 或纯文本行数），否则没法定位视口。
3. 滚动时**只重建进入视口的**，出去的要丢。

这三条是下一步的工作。

---

## 虚拟化接进 U1 之后（2026-11-03 10:40 实测）

`docs/virt.md` 的原型接进了 `cmd/app`：固定高度盒子 + 视口判断 + 视口外只放 `f.Slot`。

| `-tail` | 虚拟化前 | **虚拟化后** | 降幅 |
|---:|---:|---:|---:|
| 40 | 99.1 MB | **72.2 MB** | -27% |
| 100 | 128.4 MB | **77.3 MB** | -40% |
| **200** | **172.9 MB** | **80.8 MB** | **-53%** |
| 400 | — | **86.8 MB** | — |

CPU 同步下降：200 条从 **4.16 s → 0.47 s（-89%）**。

**而且增长变成了亚线性**：40 → 400 条（10 倍）只涨 14.6 MB，因为视口外只占一个 Slot。

### 结论

**"每条 0.46 MB"那条线性规律，只对"画出来的消息"成立。** 视口外的消息是 ~100 字节。
所以长会话的代价不再是 O(条数)，而是 O(视口大小)——**这就是要虚拟化的全部理由，现在有数了。**

`docs/virt.md` 里推算的 86.8 MB（200 条），实测 **80.8 MB**，比推算还好 6 MB。
