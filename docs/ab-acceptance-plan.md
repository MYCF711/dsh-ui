## 1. 比较单位：是「界面 + 宿主」整套，不是「界面」

UIPLAN 要的是"同任务 A/B 不劣于官方"（UIPLAN:116）。落成可执行的定义：

- **A 臂（官方）** = 官方桌面版 Electron 应用 + 它自己的宿主；目录名 `official/`。
- **B 臂（新版）** = `cmd/app` 原生界面 + `dshd serve`（`../DSH-GO`）；目录名 `native/`。

因此：

1. token 与墙钟的差异**可能来自宿主而不是界面**，报告里不许归因到界面（本仓 AGENTS §1："已有部件不等于官方包全部行为完成"，同理"界面快 ≠ 整产品快"）。

3. 10 个样本只报原始值，**不报显著性**（UIPLAN:151 明令）。

### T07 · 长会话定位：在最近 1000 条里逐字引用 【policy=allow】

**夹具**：准备阶段从一个真实大会话（≥3000 条；本机存在 7526 条 / 41.5 MB 的那份，`docs/product-acceptance.md`:38）里，用脚本从**最近 1000 条**挑一个出现 ≥3 次的关键词，写进 `prompt.txt` 的占位符里（挑不到就换关键词，不许改判据）。

**提示词（`<KW>` 由夹具填）**

```
这是一个人工挑选的真实长会话，窗口里是最近 1000 条。请找到最近 1000 条里出现过 <KW> 的一条工具输出，
原文引用其中一行（≤60 字），并写出它属于哪一轮：把那一轮用户消息的**开头 8 个字**原样抄下来。
不要凭印象编，两处引用都必须逐字存在。
```

> 为什么不要求"第几轮"：本机一份真实会话实测 `user/message` 161 条而 `turn/start` 只有 46 个（§5.2），"轮"的定义会打架；用"该轮用户消息开头 8 字"做锚点，机器能唯一复位到某一轮。

**成功判据**

| # | 判据 | 类型 | 采集/复核方式 |
|---|---|---|---|
| M1 | 引用串在 journal 最近 1000 条里**逐字**存在（去 JSON 转义后 grep） | 机器 | 脚本 |

## 4. 尝试、重置与成功率

### 4.1 一次「尝试」（attempt）的定义

**一次尝试 = 从复位后的干净起点开始，到下列任一终止条件为止的一段完整会话**：

1. 全部机器判据 + 人判判据达成 → **成功**；
2. 操作员判定不可能在本任务时间上限内完成（走错方向、卡死、崩溃）→ **失败**；
3. 达到该任务的单次时间上限（10–20 分钟，见各任务）→ **失败**。

同一任务第 2、3 次尝试必须**复位工作区 + 新建会话**，不许在失败会话里接着改（否则 token 与墙钟不可比）。复位命令与结果哈希写进 `env.txt`。

### 4.2 上限：**最多 3 次**（写死）

- 每个任务、每一臂最多 3 次尝试，**不许因为想赢而加第 4 次**。
- 同一任务 3 次都失败 → 该任务在那一侧记"未完成"，并且**不许事后放宽判据**。

### 4.3 成功率定义：**「最多 3 次内完成」**（写死，不用"第几次完成"）

```
某侧成功率 = 该侧"在 ≤3 次尝试内达成全部判据"的任务数 / 10
```

- 这是**任务级二值**：第 1 次成功、第 3 次成功，对成功率贡献相同。
- 另**单独**记录「第几次成功」（1/2/3）作为分布，**不参与**成功率，只用来解释"是稳定性问题还是能力问题"。
- 不采用"必须在第 1 次完成才算"的严格定义：官方侧本身也会失败一次（模型抖动），那会把差异变成噪声；3 次是本方案给的**上限而非配额**。

### 4.4 顺序

- 奇数任务**先跑官方臂**，偶数任务**先跑新版臂**，抵消"后跑的那一臂模型更热/机器更闲"的时段偏差。
- 同一任务的两次跑必须在同一小时内完成；跨小时要重跑先跑那一侧的最后一个 attempt，确保同一时段可比。

| **净墙钟** | 墙钟 − 人工耗时（近似值，含操作员思考时间差） | 计算 | `metrics.json` | 机器 |
| **轮/步数** | `turn/start` 数 / `step/start` 数 | journal 计数 | `metrics.json` | 机器 |

### 5.2 token 怎么采（口径与可行性都实测过）

会话原始日志：`<home>/sessions/<projectKey>/<sessionId>/session.v4.jsonl.zstd`（`../DSH-GO/internal/session/log.go:36-37`）。事件形如 `{type,seq,time,data}`，助手事件带 `data.usage`，字段名 `inputTokens/outputTokens/totalTokens/cacheReadTokens`（`../DSH-GO/internal/transport/api.go:62`）。

本机可行性实测（2026-11-03，只读）：

```bash
python3 -c "import zstandard; print(zstandard.__version__)"   # → 0.25.0，已装
```

对一份真实会话（`--D-DeepSeek~0020Harness-default-workspace-DSH-GO--/02fa485f-…`）解压统计：**3272 行、429 个 `step/start`、428 条 `assistant/message`、46 个 `turn/start`、412 个 `tool/call`、415 个 `tool/result`**。带 usage 的事件 429 个（428 条 `assistant/message` + 1 条 `compaction/summary`），**ΣtotalTokens = 208,239,656**；只算助手消息是 **207,700,058**（差 539,598，0.26%）。

→ 所以口径要写死一条：**"所有带 usage 的事件都算"**（含压缩摘要），两臂同一实现、同一选择；上面这 0.26% 就是"只算助手消息"与"全算"的差，换个选择就换个数，不许一臂一套。

这说明：**两臂都用同一段脚本就够，不需要界面配合**——这也是选择 journal 而不是"读界面状态栏"的原因（状态栏是产品自报，且官方侧读不到）。

**脚本接口（待建，不在本包范围）**：`scripts/ab-metrics.py <session.v4.jsonl.zstd>` → 打印 JSON（下面是**字段形状示意**，数值不是本次任务的实测）：

```json
{"turns":46,"steps":429,"tool_calls":412,"tool_results":415,
 "tokens_total":208239656,"tokens_in":0,"tokens_out":0,
 "wall_ms":0,"first_ts":0,"last_ts":0}
```

> **必须同一实现算两臂**。脚本要在两臂的 journal 上都跑过一遍并给出相同字段，否则口径不可比。

**一条必须写在报告里的坑**：同一份会话里 `user/message` 有 **161** 条、`turn/start` 只有 **46** 个（同上实测）。所以"用户消息条数"**不能**当轮次用；轮次一律用 `turn/start`，返工次数用 `interventions.jsonl` 并只用 `turn/start` 做上界校验。

### 5.3 返工次数怎么数（必须先列清单，不能事后解释）

| 编号 | 计入返工 | 说明 |
|---|---|---|
| R1 | 纠正性追问 | 模型走错方向后，操作员追加指令让它改回来 |
| R2 | 手动改产物 | 操作员自己编辑了助手该写的文件 |
| R3 | 手动补验证 | 操作员自己去终端跑了助手没跑的命令 |
| — | **不计** | 任务规定的审批点击（T05/T06）、任务规定的重启界面（T04）、任务规定的产品新建会话/切会话 |
| R5 | 澄清回答 | 助手主动问、操作员回答。**单列**，不计入返工，但记录（"好产品应该少问"） |

**人工耗时的实测方法**：审批从条出现到点击；操作员的每次主动操作记起止（同一块表）。精度取秒即可。

### 5.4 判定口径必须避免的三个坑

1. **不拿"气泡消失"当审批生效**（AGENTS §4、UIPLAN U-R8）：审批只认 `optionId` 回传 + 文件/工具结果。
2. **不拿"界面状态栏数字"当 token**：那可能只显示上下文而不是累计（本仓 `usage` 有 nil 与 0 的区分，`../DSH-GO/cmd/dshd/transport_source.go:369-377`）。统一从 journal 算。
3. **不拿"进程还活着"当成功**：每个任务的判据都是产物（文件/测试退出码/journal 帧），不是画面。

## 7. 反作弊：怎么保证不比"谁先拿到答案"

1. **产物必须可被第三方复核**：每个任务的判据都落在文件、测试退出码或 journal 帧上，没有一条是"助手说完成了"。速度只在产物合格之后才被记录。
2. **测试由第三方在干净目录重跑**：A/B 结束后，把 `ws-<arm>` 复制到 `clean/`，用固定命令重跑（`go test` / `go build`）。助手"改了测试让它过"会在这次独立重跑里暴露（T02 另有测试文件 sha256 的硬比对）。
3. **反证必须出现**（T10）：要求助手自己把快照改坏、看到红、再恢复。执行者**独立复现一次**——不收助手的自述。
4. **不许改测试文件**（T02）：与夹具基线比 sha256，动了就是不通过，哪怕测试绿。
5. **答案不来自产品自报**：token 从 journal 算、墙钟从 `time` 字段算、审批从 `optionId` + 文件是否存在判、长会话引用从 journal 原文 grep。官方侧即使有更漂亮的"已用 token"数字也不用。
6. **快照里没有历史可抄**：`git archive` 产物不含 `.git`（§3.4），助手不能"翻提交历史找上次怎么写的"。
7. **每次尝试复位**：`robocopy /MIR` 后校验快照 tar 的 sha256；上一次尝试的产物不会被下一次捡到。
8. **提示词里不泄题**：不出现"A/B"、不出现"要比官方快"、不暗示判据里的具体字符串（T05/T06 的 marker、T09 的行数都是任务本身的要求，不是答案）。
9. **人判项判定前冻结**：每个 H 判据在跑之前写成二值问题（"解释里是否指出需要用户授权：是/否"），跑完只允许回答是/否，不允许改成"还不错"。
10. **顺序抵消**（§4.4）：奇偶任务交替先后，避免"后跑的那臂更占便宜"被读成产品差异。

## 9. 前提与限制

### 9.1 为什么本方案**只设计、不执行**

| 限制 | 事实 | 后果 |
|---|---|---|
| **官方侧必须人跑（不能由我启动 Electron 应用）** | 官方是 Electron 应用；本会话自己就跑在官方侧（`DSH_HOME=D:\DeepSeek Harness\home`、`DSH_PROFILE=desktop`），同一 profile 不能并行再起一个实例；且本机 AGENTS 铁律禁止我重启/关闭 DSH | 官方臂的每一步（启动、点审批、切会话、截图）只能由真人做；**本方案因此只设计、不执行** |

### 9.3 有效性与成本限制

1. **10 个样本不做统计推断**（UIPLAN:151）。只报原始值 + 逐任务判定。
2. **两臂串行、同机**：本机无 CPU 隔离（`docs/perf.md`:69），所以每任务的两次跑限定在同一小时内（§4.4）。本方案的指标里**没有**内存/CPU，A/B 不量性能（性能另有 `docs/perf.md` 与 PERF 包）。
3. **成本估算**【设计值，首轮后校准】：每臂约 35 轮，模型侧单轮从 prompt 到调工具实测 60–90 秒（`docs/progress.md` 2026-11-03 19:40 那条），加工具执行每轮约 2 分钟 → 每臂 ≈ 70 分钟纯执行；按平均 1.7 次尝试 → 每臂 ≈ 2 小时；两臂 + 准备/记录 ≈ **一轮 A/B 约 5–6 小时**，需要至少 2–3 个真人时段。
4. **官方侧临时 home 的两个未知**：官方应用是否采用 `DSH_HOME`；空 home 是否会走首次配置引导。若官方起不来或起不到"可用"状态，**降级方案**：官方臂使用真实 home、每次任务新建会话，并在报告里标注"home 未等价"。降级后 token/返工仍然可比，但"会话列表干扰"这一项要单列。

## 11. 判定与报告

### 11.1 三个门槛（UIPLAN:151 原文的落法）

| 门槛 | 判定 | 不过怎么办 |
|---|---|---|
| 新版任务成功率 ≥ 官方 | 10 个任务的二值成功率直接比 | 任一任务在新版侧 3 次失败而官方侧成功 → 该任务记为**失败项** |

| 新版 token 中位数 ≤ 官方 | 同上，用 `metrics.json` 的 `tokens_total` | 变差 → 失败项 |
| （观察项，不设门槛）墙钟 | 报原始值 + 轮/步数 | 若明显更慢，人工复核是否界面卡顿，只作观察记录 |
