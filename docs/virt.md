# 视口虚拟化原型：500 条从 94.2 MB 降到 58.5 MB

> 2026-11-03 10:00 · `spike/virt/`（独立原型，没碰 `cmd/app` 和 `internal/`）· Windows 11 / Go 1.27.3 / `CGO_ENABLED=0`

## 一、原理（三句话）

1. **每条消息放在固定高度的盒子里**（估算高度），所以累计位置永不漂移。
2. **视口外的消息只放 `f.Slot().Height(h)`**——不建 `f.Text`，也就不生成 GPU 文本纹理。
3. 视口位置每次从 `m.view.ScrollState(id).Offset` 现取（**不长期持有指针**，`flex/scroll.go:15-18` 的原话）。

```
y = 0
for i, msg := range msgs {
    h = heights[i]                       // 估算，不渲染也能算
    inView = y+h > offset-overscan && y < offset+viewportH+overscan
    if inView { 真实渲染（固定高度盒子 + MaxLines） } else { f.Slot().Height(h) }
    y += h
}
```

## 二、三档实测（500 条，每条 200–500 字）

| 模式 | 渲染条数 | WorkingSet | CPU |
|---|---:|---:|---:|
| `all`（全渲染） | 500 | **94.2 MB** | 1.98 s |
| `viewport`（只视口） | ~5 | **58.5 MB** | **0.14 s** |
| `overscan`（视口 ±1 屏，默认） | ~15 | **60.4 MB** | 0.17 s |

**内存降 38%，CPU 降 93%。**（CPU 降得更多，因为布局树小了）

`overscan` 只比 `viewport` 多 1.9 MB——**这 1.9 MB 买的是滚动平顺**，值得。

截图：`virt-all.png` / `virt-viewport.png` / `virt-overscan.png`

## 三、估算公式（以及我踩的坑）

```go
usable  := 宽度 - 40                      // 两侧 padding
perLine := usable / (fontSize * 0.62)     // ← 0.62 是实测反推的
lines   := ceil(字符数 / perLine)
height  := lines*22 + 20                  // 行高 22 + 上下 padding
```

### 坑：第一版系数用 1.0，每条高估 50%

`perLine := usable / fontSize`（以为中文 1 字 = 1 个 fontSize 宽）。

实测结果：**每条下面拖一条大空白**（估算 6 行、真实 4 行）——见变更前的现象。

改成 **0.62** 之后留白消失（`virt-overscan2.png`），代价是偶尔末尾被裁一行（第 3 段那句 `01…`）。

**说明**：中英混排的实际行宽不是 1.0 × fontSize——英文比中文窄得多，`0.62` 是这批文本的实测中位数。

## 四、跳不跳：**不跳**

这是本原型最关键的结论。

| 现象 | 会不会发生 | 为什么 |
|---|---|---|
| **滚动时位置漂移** | **不会** | 每条是**固定高度盒子**，累计位置只由估算值决定，与真实渲染无关 |
| 估算偏大 | 留白 | 盒子比文字高，字不会溢出 |
| 估算偏小 | 末尾被裁 | `MaxLines` 截断，不溢出盒子 |
| **滚回来时内容变了** | **不会** | 高度表是常量，不依赖"上一帧渲染了什么" |

**代价是"精度换稳定"**：不追求每条高度精确，只保证**位置可预测**。这跟 Web 的 `content-visibility: auto` 是一个思路——用占位尺寸换渲染量。

## 五、推到真实会话能到多少（**推算，不是实测**）

`docs/u1-memory.md` 测到真实会话每条 0.46 MB（长文本 + 纹理），基线 80.8 MB：

| 场景 | 内存 |
|---|---:|
| 现在（200 条全渲染） | 172.9 MB（实测） |
| 虚拟化到视口 ±1 屏（约 13 条） | **80.8 + 13×0.46 ≈ 86.8 MB**（**推算**） |

**目标是 90 MB 以内，推算值 86.8 MB——够，但余量只有 3 MB。**

**要证伪这个推算**，得把 `cmd/app` 接上（父代理的下一步），届时实测。

## 六、接进 U1 要做的事

1. `cmd/app` 的消息列表改成这个结构（固定高度盒子 + 视口判断）。
2. 高度估算要用**真实会话**校准（`0.62` 是我这批 seed 文本的系数，AGENTS.md 那种长文本可能不同）。
3. 视口外的消息**不要**进 `mdDocs` 缓存（现在按消息下标缓存，等于视口外也在排 Markdown）。
4. `overscan` 用 1 屏（实测只多 1.9 MB）。
